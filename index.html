Estimated guess rank scoring engine
Instead of an additive point score, this engine estimates how many guesses a smart attacker would need before reaching this password. This is how tools like zxcvbn reason: a dictionary word used as a base is found in thousands of guesses regardless of how many symbols surround it; a truly random string requires brute force across the full keyspace. The two numbers are not the same thing, and are not presented as the same thing.

Pattern detections
Each detected pattern replaces the relevant portion's guess contribution with a more realistic (lower) estimate. Undetected portions fall back to character-distribution heuristics. This is a simplified version of how zxcvbn assembles its estimate. Important limitation: this tool evaluates each pattern independently and takes the minimum guess estimate. Real cracking tools (hashcat with rule files, PCFG crackers) combine multiple patterns simultaneously — a password matching dictionary + year + mask is often faster to crack than any single estimate implies, because the attacker runs wordlist × rules × masks in parallel, not sequentially.
Entropy — three numbers, three different things advanced
⚠ Misleading terminology warning: "entropy" means different things in different contexts. All three numbers below are shown so you can see what each one captures — and what it misses.
Max theoretical entropy
—
log₂(pool^len) — assumes every slot is an independent uniform draw from the full charset. Upper bound. Not the real entropy of this specific string.
Character-distribution entropy
—
Shannon entropy of this string's symbol frequencies. Catches single-char repetition (aaaa→0 bits) but not alternating patterns (ababab→12 bits despite being predictable).
Heuristic effective entropy estimate
—
min(theoretical, repetition-corrected distribution). A heuristic invented for this tool — not a standardized or published metric. Used for scoring because it is more conservative than either component alone. Do not cite this as an industry standard.
Approx. inspired by NIST SP 800-63B not an official formula
—
Simplified diminishing-returns model. SP 800-63B does not publish a bit-scoring algorithm — this is an illustrative approximation only.
The only entropy number that actually matters for predicting real-world crackability is the guess rank above — because that accounts for attacker knowledge (wordlists, patterns, mutations), not just the string's mathematical properties in isolation.
What entropy does not tell you — and why this matters. Every entropy formula here assumes the password was generated by a random process. That assumption is almost never true for human-chosen passwords. A string like aaaaaaaaBBBBBBBB!!!! has high character-distribution entropy (it uses three distinct character classes across 20 positions) yet is practically worthless — the structure is immediately obvious, and the repeated segments collapse the real unpredictability to near zero. This is a false positive: a high entropy reading on a weak password. The heuristic detectors above attempt to correct for the most common cases, but no formula fully closes this gap. The reverse problem also exists. R8$#LmQvPz looks strong by every metric here — high entropy, no detected patterns, no dictionary hits. It probably is strong as a standalone password. But if it is reused across ten accounts, and one of those services suffers a breach and stores passwords in plaintext, the password is effectively compromised everywhere simultaneously. No local analyzer can know this. Reuse converts a strong password into a single point of failure, and no entropy calculation captures that risk. The practical ceiling of any entropy metric: entropy measures mathematical uncertainty under a specific model. It does not measure how much an attacker knows, what data they have already breached, or whether this exact string appears in a database somewhere. "100 bits of entropy" does not mean "secure forever" — it means "an attacker with no prior knowledge, using brute force, would need on average 299 guesses." Real attackers are rarely in that position.

Leet-speak normalization attack trick
Attackers apply character substitutions before checking against dictionaries. This demo covers single-character substitutions only. Real rule engines (hashcat, John) also handle multi-character graphical substitutions: vv→w, ()→o, |<→k, \/→v, \/\/→w — these cannot be shown as a simple character-level normalization.

Example hardware configurations can compute ~10¹¹ SHA-256 hashes/sec — exact rates vary widely by GPU, cluster size, and implementation. English Bigram Similarity simplified — not a real Markov model
⚠ This is English bigram similarity analysis, not a Markov model: it uses ~50 hardcoded bigram frequencies from English prose — not password data, not multiple languages, not conditional probability chains. A real Markov password model would be trained on breach corpora and produce P(char | previous chars), not P(bigram) from a table someone typed by hand. What this actually detects: whether letter pairs in your password resemble common English. That's a much weaker signal than it sounds.
What this section is not: a real Markov password model trains on millions of breached passwords and produces conditional probability distributions over character sequences. This tool uses ~50 hardcoded English bigram frequencies — it is an "English prose resemblance" detector, not a password probability estimator. The score below tells you whether your password looks like English, not how likely a Markov-based cracker is to find it quickly. Those are related but not the same thing.

PCFG (Probabilistic Context-Free Grammar) cracking learns common password structures from breach data — e.g. that Word + Year + Symbol is extremely common — and generates guesses in structural-likelihood order rather than alphabetically. It's why a password like Summer2024! falls quickly despite looking "complex": the attacker isn't guessing characters, they're guessing the template.

Password reuse conceptual
⚠ The blind spot every single-password tool has: GooglePassword123!, GithubPassword123!, and NetflixPassword123! each score well individually. In reality, once any one service breaches, the structural pattern is immediately obvious and the rest are tried automatically. A unique, unrelated password per site matters more than any individual password's internal strength.
Contextual passwords — a class this tool cannot detect
Some passwords appear structurally strong by every metric here but are semantically obvious to anyone with the right context:
Tesla2026!        → company name + year + symbol
JohnSmith2012     → personal name + surname + year
GoogleIntern2026  → employer + role + year
MicrosoftAzure!   → company + product + symbol
LiverpoolFC       → sports team + abbreviation
These passwords contain company names, personal names, sports teams, organisations, events, and popular brands. A generic password checker has no context about who is typing, so it cannot detect them. Professional crackers targeting specific organisations or individuals build custom wordlists from LinkedIn profiles, company wikis, sports databases, and public social media — turning contextual knowledge into a targeted attack. No static dictionary covers this. The practical implication: a password that no one who knows you could guess is a separate requirement from one that scores well on any automated tool.
What a production tool would add
The gap between this demo and a professional analyzer (like Dropbox's open-source zxcvbn) is almost entirely data, not code architecture: breach corpora of hundreds of millions of real passwords; trained Markov and PCFG models; keyboard adjacency graphs for all standard layouts; ranked name databases; international dictionaries; date-format detection across multiple locales; years of tuning against real human behavior. The structural approach here (pattern detection → guess rank → per-scenario crack time) is the same approach those tools use — this demo just can't ship 30GB of training data into a single HTML file.
Known limitations & disclaimers
🌐 Language scope — currently English only. This tool's dictionary, pattern detection, and English Bigram Similarity analysis are built exclusively on English-language data. Passwords in other scripts (Arabic, Devanagari, Cyrillic, Chinese, etc.) or romanized non-English words will be treated as character sequences with no semantic detection — their guess rank will be estimated from character distribution alone, likely producing an overestimate of actual security. Expansion to multilingual dictionaries, script-aware pattern detection, and non-Latin keyboard adjacency graphs is a planned future improvement.

English Bigram Similarity

The feature labeled "English Bigram Similarity" uses approximately 50 hardcoded bigram (letter-pair) frequencies derived from English prose text. It is not a Markov password probability model.

Professional password crackers typically use:

  • Large probabilistic Markov chains
  • Conditional probability models (P(char | previous chars))
  • Training on millions of leaked passwords — not prose
  • Multiple languages and writing systems
  • Statistical weighting of character sequences

This feature should be interpreted as an educational demonstration of language pattern detection, not a complete probabilistic password estimator.

Crack time estimates

All displayed crack times are illustrative examples only. Actual cracking speed depends on many variables:

  • Hardware — single GPU vs. farm vs. cluster
  • Password hashing algorithm (MD5, bcrypt, Argon2id, PBKDF2…)
  • Hash configuration and cost parameters
  • Attack strategy — brute force vs. rules vs. PCFG
  • Whether the hash is salted

Where hardware rates are shown, they represent example configurations only — not specific equipment. Actual cracking speed depends on GPU model, number of GPUs, hash algorithm, memory hardness (bcrypt, Argon2id, scrypt all differ), whether distributed cracking is used, and available budget. Rates shown become outdated as hardware improves and should be treated as illustrative order-of-magnitude values, not predictions.

Rule-based, not probabilistic

This tool evaluates password weaknesses using separate heuristic rules — dictionary words, keyboard walks, dates, repeated characters, common suffixes — independently. The lowest guess estimate across all detectors is used as the dominant score.

Professional password auditing systems combine these simultaneously using probabilistic scoring. A password matching dictionary + year + mask is often faster to crack than any single-vector estimate implies, because real tools run wordlist × rules × masks in parallel.

Implementing a full probabilistic estimator requires substantially larger datasets and statistical models beyond the scope of this project.

Limited contextual knowledge

The system cannot recognize every context-specific password. Examples this tool may overrate:

  • Personal names + surnames + dates (JohnSmith2012)
  • Employer or role references (GoogleIntern2026)
  • Company + product combinations (MicrosoftAzure!)
  • Sports teams and players (LiverpoolFC)
  • Institution-specific terms not in the dictionary

Professional crackers build targeted wordlists from LinkedIn profiles, company wikis, sports databases, and public social media. No static dictionary replicates this. Scoring well here and "unguessable to anyone who knows you" are two different requirements.

Dictionary coverage

The built-in dictionary contains approximately 10,000 tokens derived from the top 100,000 entries of the RockYou breach dataset. Professional tools use:

  • Tens of millions of breach-derived entries
  • Ranked dictionaries across multiple languages
  • Continuously updated datasets as new breaches occur
  • Thousands of mutation rules per dictionary entry

A password not flagged by this dictionary is not necessarily safe — it may simply not appear in this tool's limited sample.

General disclaimer

No password is permanently unbreakable. Hardware improves, new attack techniques emerge, and breach databases grow continuously.

A score of "Excellent" means this tool found no patterns it recognizes — it does not mean the password is secure against all present and future attacks.

Always:

  • Use a password manager to generate and store unique passwords
  • Enable two-factor authentication on every account that supports it
  • Never reuse passwords across sites
  • Treat any automated password score as one signal, not a guarantee
